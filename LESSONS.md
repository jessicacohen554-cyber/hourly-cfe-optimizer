## Reliability Tax Redesign — Apr 18, 2026

1. **Section names must describe content, not metaphors.** "The Setup / The Hump / The Abandonment / The Tax / The Cost of Waiting" read as pretentious filler to the user. Descriptive titles using the numbered `section-header` + `section-number` pattern from `clean_firm_case.html` / `lmp_trends.html` — e.g. "Why a clean-only grid still builds gas", "How much new gas gets built", "How much of it gets stranded" — are what ships.
2. **Never cite `SPEC §` or `Card [A-Z]'` in user-facing copy.** Public readers see `SPEC §24.5`, `Card F'`, `§24.8 NOAK-2035` as internal shorthand and disengage. Methodology citations belong in `optimizer_methodology.html` and `SPEC.md`, not in hero text, chart captions, insight boxes, or footer notes.
3. **Pathway comparisons must show all pathways on one plot — toggles aren't comparisons.** The original §2 hump chart and §6 stranding chart used a pathway toggle that made users click through one-at-a-time views. Real comparison means overlay: all three pathways as colored lines in §2, all five pathways as sorted horizontal bars in §6. A toggle that hides the other options isn't a comparison, it's a slideshow.
4. **Industry acronyms get defined on first use per page, not banned.** ELCC, NOAK, FOAK, LCOE, CCS, LDES, 45Q, 45U, ITC, PTC, ATB, LOLE, CFE, VRE, BESS, CCGT, IPP, ISO, AEO, NREL, LBNL, EIA, NERC are legitimate terms for this audience — the fix is a parenthetical expansion on first occurrence, then the bare acronym thereafter. Stripping them entirely dumbs the copy down; leaving them undefined locks out readers.
5. **Prose-fixer agents (`jargon-fixer`, `voice-fixer`) replaced the originally proposed pre-commit jargon hook.** A regex-based git hook can't tell whether `ELCC` was already defined earlier on the page, or whether `LOLE` in a chart tooltip is a legit second-use or an undefined first-use. Both require reasoning about page-scoped context. Sub-agents invoked via `/fix-jargon`, `/fix-voice`, and `/fix-prose` handle that context-aware rewrite; a hook would false-positive on every clean page and miss the genuine problems.

## Coding-Session Agent — Apr 18, 2026

6. **Code-task sub-agents must force a reference read before any output.** Pattern-matching from a filename ("this looks like a chart-payload generator") produces wrong code — every chart-payload generator in `reliability_tax/charts/` has subtle differences in how it resolves paths, caches loaders, and names output keys. The `coding-session` agent makes the full read of the code-reference-table exemplars a **Phase 1 gate** (silent, no user output until done), with the structured plan only emitted after. This is the code-side analog of what `jargon-fixer` does for prose: encode the workflow in the agent so the model can't downshift to a shortcut when the task "feels mechanical."

## Pipeline-Audit Agent Hardening — Apr 19, 2026

7. **Long-running review agents must land artifacts incrementally, not at end-of-run.** The original `pipeline-audit-agent` dumped everything at Phase 6; the first live run hit its tool-call budget mid-Phase-4 and produced zero usable output. The fix was not a tool-call cap (that caps rigor), a "partial verdict at 80%" trigger (arbitrary), or end-of-phase checkpoints (still too infrequent + implied stopping). It was **writing each material finding the moment it surfaces** — the file at `<feature_dir>/AUDIT_<date>_<target>.md` opens at Phase 0 with a `## Findings` section header, then grows live as the agent discovers specific observations (price-table cell out of range, function misaligned with intent, timing constant creating an unintended mechanism). Writing a finding is not a stopping decision — the agent keeps running, the file is already mostly a memo by the time Phase 5 appends the verdict. PARTIAL only fires on hard blockers (missing cached outputs, unreachable source), not on time pressure. Pattern generalizes: any multi-hour review agent should write its evidence trail live, and reserve the final "stop and write the memo" step for structural summary only.

## Parity probes don't cover flag-gated code paths — Apr 19, 2026

8. **A parity probe with the new-behavior flag OFF does not validate the new-behavior code path.** f060d38 endogenized gas-build cost in the optimizer's argmin and passed its parity probe bit-for-bit on ERCOT P1 ep80 and PJM P3 ep90 — both with `INCLUDE_GAS_COST_IN_ARGMIN=False`. That gave false confidence: the OFF branch never calls `score_ef_batch_with_gas`, so a real defect on line 1853 — `pc.WHOLESALE_PRICES.get(iso, {}).get('Medium', 0.0)` against a flat scalar dict — shipped unexercised and crashed the very first sanity-probe attempt with the flag ON. Rule for future flag-gated rollouts: a parity probe must cover **both** branches before the commit lands. Minimum bar: (a) flag=OFF reproduces cached baseline bit-for-bit (necessary), AND (b) flag=ON completes end-to-end at ≥1 config and writes its expected output JSON (necessary). The ON-run doesn't need to match the OFF-run — it just needs to prove the new code path executes. A 30-second import-smoke (`python -c "from step_2_3_pathway_optimizer import score_ef_batch_with_gas"` + a 5-row fixture call) would also have caught this. Cost of skipping: a wrapped session with zero probe data; cost of the rule: minutes.

## Grep for existing optimizations before estimating probe cost — Apr 19, 2026

9. **Before estimating the wall-clock cost of a multi-run probe, grep for an existing in-process driver.** This session's 12-config probe was scoped as 12 separate `python3 step_2_3_pathway_optimizer.py ...` invocations with a "10–20 min" time estimate — the user immediately pushed back ("The code shouldn't take this long to run that indicates a lack of optimization"). One `Glob scripts/*pathway*` revealed `scripts/_sweep_pathways_inproc.py`, a working driver whose own docstring documents the problem: subprocess-per-config pays ~5.7s of numba/parquet cold-start per run plus reloads the dispatch cache, all avoidable by keeping one Python process hot for an entire ISO's runs. Revised probe cost using the in-proc driver: ~1–1.5 min, ~10× cheaper. The orchestrator `run_pathway_sweep.py` has the same regression — it calls `subprocess.run` per config and never imports the in-proc driver, so the full 350-run v2 sweep likely wastes 5–10× its wall-clock too. Rule: any time a probe plan involves N invocations of the same script, grep the scripts/ dir for an existing "inproc", "sweep", "driver" variant first. If one exists, use it. If one doesn't and N > 3, write the trivial loop that imports the module once and calls `main(...)` in-process — don't scope N subprocess invocations.

## Profile one run before committing wall-clock to a multi-run probe — Apr 19, 2026

10. **"Should be fast per the docstring" is not a profile — measure before launching N runs.** After the subprocess-per-config regression was identified and the in-proc driver's docstring was quoted as the cost baseline (~0.5–1s per run after cold-start), the next probe attempt still drew a "it shouldn't be idling or taking this long" interrupt from the user before launch. Lesson: a docstring is an authored claim, not a measurement — it can go stale when upstream modules change (numba recompile hazards, parquet schema drift, pandas version bump, new per-year operation added to `run_pathway`). Before committing wall-clock to 12 runs (or 350), profile **one** run under `cProfile` with `--endpoints 0.90 --pathways 3` and confirm the shape: cold-start cost paid once (numba JIT + parquet load + EF-table load), hot-loop cost per run matches advertised. Top-20 cumtime offenders from a single run surfaces any regression (per-year recompute, per-endpoint reload, an accidental Python loop) for < 30s of wall-clock. If the profile is clean, launch the full sweep with confidence; if it's dirty, fix the hot spot first — because whatever burns wall-clock at 12 configs burns it 30× worse at 350. Rule: multi-run probes get a one-run profile gate, always.

## Per-year cache-persist inside a solve loop is a silent wall-clock killer — Apr 19, 2026

11. **Any disk-write-per-iteration inside a 26-year solve loop must be hoisted out of the loop.** The §24.9 probe "appeared to idle" because `solve_pathway::for year in YEARS:` (`scripts/step_2_3_pathway_optimizer.py:2344`) calls `size_required_gas_mw` → `worst_hour_gas_sizing` → `_worst_hour_residual_norm` → `_expand_missing_archetypes` → `expand_cache_for_mixes(..., persist=True)` → `save_dispatch_cache()` per year — and `save_dispatch_cache` serializes the **entire** ~100 MB dispatch-cache parquet to disk. If each year introduces a novel archetype (target-mix changes annually in most pathways), that's up to 26 full-parquet writes per `run_pathway` call, 0.1–0.3s each, with zero stdout — the runs look hung but are actually mid-serialization. Fingerprint: the ERCOT parquet grew 47 MB → 110 MB in a single session from import side-effects alone. Fix pattern: thread a `persist=False` flag through the year loop, collect novel archetypes in-memory, persist **once** at the end of `run_pathway`. General rule: any "cache grows monotonically, persist=True by default" pattern is safe in a one-shot CLI but lethal inside a solve loop — audit every `persist=True` site for loop-containment before running a multi-run sweep. A code-only exploration against `run_pathway` (no execution) caught this in one Explore pass — cheaper than any profile would have been, because `cProfile` would have reported the write as `pyarrow.parquet.write_table` without explaining why it was called 26 times.

## Session-start pip install and root-level one-shot prompts silently tax every session — Apr 19, 2026

12. **`.claude/` hooks and root-level one-shot prompt files compound into session-wide drag — audit them before asking "why is Claude slower."** Two separate cost drivers found in the same hygiene pass: (a) `.claude/hooks/session-start.sh` unconditionally ran `pip install --quiet numpy pyarrow numba` every remote session (15–30s blocking wall-clock), fixed by an import-guard that short-circuits when packages are present (0.97s on warm env, confirmed); (b) ~4,600 lines of root-level one-shot prompt scratchpads (`HYBRID_AUDIT_*`, `hybrid-session-prompts*`, `hybrid_integration_fix_prompts`, `RELIABILITY_TAX_4.7_BAKEOFF`, `STYLE_GUIDE` superseded by `DESIGN_SYSTEM`, stale `contrast-audit-report.md`) got skimmed during file-listing and directory-orientation phases of every session, diluting the signal of the canonical docs. Pattern: any one-shot prompt file is disposable once its work lands — treat it like a shell history entry, not a source of truth. Same pattern for thin wrapper slash commands that duplicate their underlying agents (`/fix-jargon`, `/fix-voice`, `/fix-visual` deleted; only `/fix-prose` that genuinely orchestrates survived). Same pattern for overlapping agent descriptions — the parent Claude's subagent-selection gets noisy when two agents sound interchangeable. Rule: audit `.claude/` and root-level doc cruft when session performance feels off — the fix is usually subtraction, not tuning. Structural hygiene beats knob-twiddling.

## Silent SIGKILL mid-archetype-expansion in the §24.5 A/B — Apr 20, 2026

13. **A hot-process driver that prewarms once and runs all four ERCOT (pathway, endpoint) combos back-to-back exceeds sandbox RSS during archetype expansion and dies without a traceback — plan for one-combo-per-process as the portable form.** `scripts/_surrogate_ab_driver.py` is shaped as a single Python invocation that (a) `prewarm_caches` the two endpoints, (b) sets `iso_state['deferred'] = True` to hoist the archetype-write out of the year loop, (c) loops 4 combos × (truth, surrogate). On this gVisor sandbox it got as far as `[ab] TRU pathway=3 ep=0.8 ...` and then streamed `[expand] ERCOT: archetype N/2861` lines up to 2,761 before the process was SIGKILL'd mid-print — output cut off inside the "archetype 2761 reconstructed in …s" line, no traceback, no `dmesg` OOM entry (gVisor container OOMs aren't kernel-logged), no `[ab]` completion line, and the driver's `finally:` block never ran so no `ab_summary.json` was emitted. Fingerprint for this failure mode: log ends mid-token instead of on a newline; memory sampled post-kill is abundant (the reaped RSS has already been returned). Two prerequisites for this attempt that should also be encoded in LESSONS: `scripts/step2_2a_cost_optimization.py` hard-imports `sklearn.cluster`, `sklearn.ensemble`, `sklearn.metrics`, `sklearn.preprocessing` (the §24.5 HistGBM surrogate host) but `scikit-learn` was never pinned in `requirements.txt` — clean env → `ModuleNotFoundError` before a single line of driver code ran. Same happened with `pandas`, which was declared but not actually installed. Rule for the next attempt: (i) `pip install -r requirements.txt` is not a real preflight — verify the modules import before launching the sweep; (ii) any multi-config driver that holds dispatch caches + 4× pathway state in one process should be restructured as N subprocess invocations with a checkpoint file (`ab_summary.json` rows appended after each combo completes) so a mid-sweep SIGKILL loses at most one combo, not everything; (iii) `iso_state['deferred'] = True` reduces I/O but does not reduce peak RSS during expansion itself — lowering RSS requires actually shrinking the working set (fewer archetypes cached simultaneously, or flush after each combo), not just deferring writes.

## Session handoff — Apr 20, 2026

17. **Offer a handoff prompt proactively when a long-running design session nears context or wall-clock limits.** The user's direction on the `claude/design-pathway-optimizer-tGKr5` plan session: if a session is at risk of timing out before the plan or implementation can finish, stop, write the plan/WIP to disk, commit + push, then output a self-contained resume prompt the next session can paste to pick up exactly where this one stopped. ## No blended LCOE for a merit-ordered resource — Apr 21, 2026

18. **When a resource has an internal merit-order cost structure (existing baseline → incremental tranches with different $/MWh), the argmin must see per-tranche cost, not a TWh-weighted blend.** Phase 3 of the step-2.3 cost-matrix fix wired `decompose_clean_firm_tranches(...)['blended_lcoe']` (a (Y, n) $/MWh matrix averaged across uprate/geo/new-nuke/CCS) into `operating_cost_matrix`. Blended LCOE hides two separable problems: (a) the Phase-2 wrapper fed `target = cf_pct × demand` including the existing-nuclear baseline, charging that baseline at uprate-LCOE instead of $0 (the ledger correctly had it at $0 — two costing conventions fought each other); (b) even if baseline were handled, a blend collapses the "first 1.7 TWh at $25 vs. next 200 TWh at $55 vs. remainder at $70" signal into one number that's equally wrong for every mix. The fix was full disaggregation: decomposer returns per-tranche (Y, n) TWh + per-year effective $/MWh, `operating_cost_matrix` sums `Σ tranche_twh × tranche_eff_lcoe × 1e6` directly (existing contributes $0 by construction), `_build_ledger` emits per-tranche vintages (`clean_firm_existing`, `_uprate`, `_geo`, `_nuke_new`, `_ccs`), and `feasibility.physical` is driven by the tranche-budget check. Gate outcome (ERCOT 6 combos vs. Phase 3): P1 unchanged, P2a/P3 at ep90 moved cf=10→20 (−7% fleet), **P2a/P3 at ep99 broke out of cf=0 collapse into cf=79 (−33% fleet, +100–144% total cost)** — directionally correct (argmin finally sees the merit-order signal and picks clean-firm at high CFE), but >50% swing triggered the escalation gate and required user sign-off before committing. Rule: any resource whose real-world stack is "first N free, next M at price A, rest at price B" must be decomposed and summed, not averaged — and the pre-existing ledger convention defines which tranches are free, not the argmin's convenience.
